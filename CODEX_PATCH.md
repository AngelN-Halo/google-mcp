
# Codex task: harden the existing Google Workspace Directory MCP Read the existing repository and README before changing anything. Preserve the current phase-one scope: read-only `users.get` and `users.list` with exactly this OAuth scope: ```text https://www.googleapis.com/auth/admin.directory.user.readonly ``` Do not add groups, Gmail, Reports, Drive, Calendar, Vault, write operations, generic HTTP access, or shell tools. ## 1. Inspect before editing First report, with file and line references: - How the FastMCP server binds inside the container. - How Compose publishes the host port. - Whether Nginx Proxy Manager can actually reach the container. - Whether MCP requests have application-level authentication. - Whether a human caller identity is captured and included in audit logs. - Whether `google_user_search` forwards caller-provided Google query syntax. - Whether service-account credentials and delegated credentials use only the approved scope. - Whether any credential path, token, private key, raw Google response, or full profile can enter logs. Do not expose secret values while reporting. ## 2. Fix container and proxy networking Inside the container, the application must bind to `0.0.0.0:8000`; binding to `127.0.0.1` inside a container prevents Docker port forwarding and peer-container access. Keep any host publication loopback-only: ```yaml ports: - "127.0.0.1:8000:8000" ``` Do not describe the service as loopback-bound internally if Compose overrides it to `0.0.0.0`. Replace use of a broadly shared `proxy` network with a dedicated MCP ingress network if practical: ```yaml networks: google-mcp-ingress: external: true ``` Attach only Nginx Proxy Manager and `google-mcp` to that network. If changing the NPM project is outside this repository, document the exact required NPM Compose addition. The MCP service should not remain reachable by every unrelated container on a general-purpose proxy network. Document Streamable HTTP proxy requirements. Preserve POST and GET behavior, disable inappropriate response buffering for streaming responses, use suitable read/send timeouts, and ensure `/mcp` is forwarded without accidental path rewriting. Do not enable permissive CORS. ## 3. Add authenticated caller enforcement and attribution NPM authentication alone is insufficient unless the application receives and verifies a trusted caller identity. Add middleware at the MCP HTTP boundary that rejects requests lacking both: - a trusted gateway secret header; and - an authenticated caller identity header. Configuration: ```dotenv GOOGLE_MCP_GATEWAY_SECRET= GOOGLE_MCP_GATEWAY_SECRET_HEADER=X-MCP-Gateway-Secret GOOGLE_MCP_IDENTITY_HEADER=X-Authenticated-User GOOGLE_MCP_AUTHORIZED_USERS=agent1@example.org,agent2@example.org ``` Requirements: - Compare the gateway secret using a constant-time comparison. - Never log the secret. - Normalize caller email case safely. - Reject missing, malformed, external-domain, or unauthorized identities. - Tool arguments must never override caller identity. - Carry caller identity and a generated/request correlation ID into every audit event. - In production mode, fail startup if gateway authentication configuration is absent. - Permit an explicitly configured test mode only in unit tests; do not silently disable authentication. Document that NPM must remove client-supplied copies of these headers and inject its own values only after authentication. Include an NPM advanced-configuration example using placeholders, not real secrets. If `$remote_user` is unavailable with the selected NPM authentication mechanism, state that limitation and require an SSO/auth proxy that supplies a verified identity. Do not pretend a shared token identifies individual help desk agents. This gateway-secret control assumes the backend is reachable only from the dedicated ingress network. Clearly document that a header secret is not a replacement for network isolation or TLS at the external boundary. ## 4. Restrict `google_user_search` The existing response example suggests the caller may submit raw Google Directory query language such as `name='Alex Rivera'`. Stop accepting arbitrary upstream query syntax. Change the public tool argument to a plain `term` or retain `query` but define it strictly as a human-entered name/email fragment. The server must construct and escape Google query syntax internally. Requirements: - Length 3 through 128 characters. - Reject control/format characters. - Reject or safely escape Google query operators and syntax; never forward the original string directly as the Admin SDK `query` parameter. - Support conservative searches for an allowed-domain email address, email prefix, or person name. - Add tests demonstrating that quotes, parentheses, `orgUnitPath`, comparison operators, wildcard abuse, and attempted query concatenation are not forwarded as raw Google syntax. - Default limit 10; hard maximum 20. - Fetch no more upstream pages than required for that bounded result. - Never expose a page token. - Retain `truncated`/`next_page_available` only if their meanings are accurate after domain filtering. If safe name-search behavior cannot be constructed reliably, support exact email and a tightly escaped name query rather than preserving a generic raw-query feature. ## 5. Support configured tenant domains safely Replace singular `GOOGLE_ALLOWED_DOMAIN` internally with `GOOGLE_ALLOWED_DOMAINS`, parsed as a non-empty comma-separated allowlist. Maintain backward compatibility for the old singular variable for one release, with a startup warning that contains no sensitive data. Use the allowlist consistently for: - explicit email inputs; - primary emails returned from search; - aliases and non-editable aliases; - authenticated help desk identities, unless a separate caller-domain allowlist is configured. Document that secondary Workspace domains must be included explicitly. Do not follow or return consumer Gmail or external-domain aliases. ## 6. Tighten audit logging Every tool call must log structured JSON containing: - UTC timestamp; - correlation/request ID; - authenticated caller identity, or an HMAC pseudonym if configured; - tool name; - masked or HMAC-pseudonymized target; - result state/count; - latency; - sanitized error category. Do not log: - gateway secret; - OAuth token; - credential JSON or credential path; - private key; - raw Google error body; - raw user record; - complete response; - full free-form prompt; - aliases or names. Add `AUDIT_HASH_TARGETS` and `AUDIT_HMAC_KEY`. Fail production startup if hashing is enabled without a sufficiently long HMAC key. Add tests that capture logs and prove representative tokens, private-key fragments, phone/profile data, gateway secrets, and raw Google errors are absent. ## 7. Review exposed status fields Keep the existing stable schema for compatibility, but add configuration that can suppress sensitive/help-desk-optional fields: ```dotenv GOOGLE_EXPOSE_ADMIN_FLAGS=false GOOGLE_EXPOSE_2SV_FLAGS=true GOOGLE_EXPOSE_LAST_LOGIN=true GOOGLE_EXPOSE_ORG_UNIT=true ``` Default admin flags to false unless existing documented approval requires them. When a field is disabled, omit it consistently or return `null` consistently; document the chosen stable behavior and test it. Do not add more profile fields. ## 8. Customer ID and deployment safety Require an explicit `GOOGLE_CUSTOMER_ID` in production. Permit `my_customer` only in development/test mode with a warning. Keep the mounted service-account key provider for this release; do not claim Workload Identity Federation support. Ensure: - the key is mounted read-only; - it is excluded by `.gitignore` and Docker build context; - the image contains no credential; - startup errors do not reveal its path or contents; - the runtime user is non-root; - the container uses a read-only filesystem and a bounded tmpfs where compatible. ## 9. Tests and documentation Add/update tests for: - missing gateway secret; - wrong gateway secret; - missing caller identity; - malformed/external/unauthorized caller; - caller identity cannot be supplied through tool arguments; - audit event includes the verified caller; - arbitrary Google query syntax is not forwarded; - search default 10 and maximum 20; - multiple allowed Workspace domains; - internal container bind address and loopback-only host publication; - only `admin.directory.user.readonly` is requested; - optional field exposure controls; - production refuses `my_customer` and incomplete authentication configuration; - logs contain no secrets or raw records. Update README architecture and threat-boundary sections so they accurately distinguish: 1. external TLS and human authentication at the gateway; 2. trusted gateway-to-service authentication; 3. individual caller authorization and attribution; 4. Google service-account/DWD authentication; 5. Google delegated-admin authorization. Include an emergency-revocation order: 1. disable/remove the NPM route; 2. stop the MCP container; 3. remove the DWD client entry if compromise is suspected; 4. disable/delete the service-account key; 5. disable the delegated admin if needed; 6. preserve and review gateway/application/Google audit logs. ## 10. Completion report Run all tests, linting, formatting checks, and type checks. Then report: - changed files; - security findings and how each was addressed; - exact OAuth scope constant; - exact container bind and host-publish behavior; - how caller identity reaches audit logs; - test/lint/type-check results; - remaining human decisions; - exact NPM and Google Admin configuration steps. Do not start the production container, modify live NPM configuration, create Google credentials, or change live DWD settings automatically.
